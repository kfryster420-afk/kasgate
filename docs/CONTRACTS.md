## Protocol constants (app/config.py)
SOMPI_PER_KAS=100_000_000, PLATFORM_FEE_BPS=150, BPS_DENOMINATOR=10_000, X402_VERSION=2,
X402_SCHEME="kaspa-exact-v1", X402_ASSET="KAS", MIN_OUTPUT_SOMPI default 20_000_000 (0.1 KAS outputs breach the 100,000 standard storage mass).
Network prefixes: kaspa:testnet-10 -> "kaspatest:", kaspa:mainnet -> "kaspa:".

## Fee split (schemas.compute_fee_split)
fee = max(ceil(total * 150 / 10_000), MIN_OUTPUT_SOMPI); merchant = total - fee, must be >= MIN_OUTPUT_SOMPI.
Minimum endpoint price = 3 * MIN_OUTPUT_SOMPI = 60000000 sompi (0.6 KAS) at the default floor (merchant output >= 2*floor, see v2.3) — schemas.min_price_sompi(). Flat 0.2 KAS fee up to 1333333333 sompi, 1.5% (ceil) above.
On-chain: outputs[0] = merchant (payTo) EXACT merchant amount, outputs[1] = treasury (feeTo) EXACT fee.
outputs[2+] allowed only as change. Generator/create_transaction keep payment outputs first.

## x402 headers (schemas.py) — Base64(JSON), standard alphabet, padded
PAYMENT-REQUIRED  -> PaymentRequired{x402Version:2, scheme, network, asset:"KAS", amount:str(TOTAL sompi), payTo, platformFee{feeTo, feeAmount:str}}
                     build with PaymentRequired.for_endpoint(price_sompi, pay_to); merchant part = .merchant_amount_sompi
PAYMENT-SIGNATURE -> PaymentSignature{txId: 64 lowercase hex, rawTx: json.dumps(kaspa.Transaction.to_dict()) of SIGNED tx, payerAddress}
PAYMENT-RESPONSE  -> PaymentResponse{txId, settled:true, network, usdValueAtSettlement: decimal string, 8 dp}
Every model has .to_header() and Cls.from_header(value) (raises ValueError).
Error JSON body: X402ErrorBody{error, message, k402: "0.2"|null, accepts: [PaymentRequired, K402UtxoOffer?]|null} (list since CONTRACT v2.9; accepts[0] is always the PAYMENT-REQUIRED terms)
error codes: payment_required, invalid_payment_header, payment_replayed, payment_expired, underpaid, invalid_fee_split,
wrong_network, tx_rejected, rpc_unavailable, service_unavailable, rate_limited, price_unavailable, endpoint_not_found, method_not_allowed, upstream_error, payment_not_found (k402 only), invalid_exact_payment (v2.10), insufficient_balance (v2.11), trial_exhausted (v2.12),
and the v2.13 refund codes: invalid_payer, invalid_signature, invalid_status, challenge_expired, challenge_replayed, refund_too_small, refund_amount_required, refund_already_open, refund_not_found, refund_not_cancellable, refund_not_claimable, refund_not_rejectable, refund_closed, invalid_payout, payout_replayed, payout_abandoned, too_many_attempts.
(price_unavailable, invalid_exact_payment and trial_exhausted were already sent but missing from this list; it now matches X402ErrorBody.error exactly. A code outside it yields a plain {error, message} body.)

## HTTP status mapping
no header -> 402 + PAYMENT-REQUIRED + body error=payment_required
bad header / underpaid / invalid_fee_split / wrong_network / tx_rejected -> 402 + PAYMENT-REQUIRED + body
replayed txId (Redis lock held or tx_id already in settlements) -> 409 error=payment_replayed
unknown/inactive slug -> 404 endpoint_not_found; method not in allowed_methods -> 405 method_not_allowed
rpc_unavailable (RpcUnavailableError) -> 503, release the Redis replay lock
Redis down on /p/* -> 503 service_unavailable (Retry-After: 5); rate limit hit on any limited route (including /v1/* and webhook test-fire) -> 429 rate_limited, X402ErrorBody `{error: "rate_limited", message, k402: null, accepts: null}`, plus Retry-After
/v1/* keeps FastAPI {"detail": "..."} bodies for 503 (limiter down, fail-closed) and other non-x402 errors
header that fails schema validation on network/address prefix -> 402 wrong_network
upstream failure after settlement -> 502 upstream_error, PAYMENT-RESPONSE still set, settlement stays SETTLED

## Engine interface (app/kaspa_engine.py)

## CONTRACT v2 — security revision after red-team testing (supersedes earlier lines where they conflict)
Payment binding (findings: mempool front-running, TOCTOU between quote and payment):
- PaymentRequired gains `nonce` (32 lowercase hex, schemas.new_payment_nonce()) and `expiresAt` (UTC, now + PAYMENT_MAX_AGE_SECONDS).
  Build: PaymentRequired.for_endpoint(price_sompi, pay_to, nonce, expires_at).
- Gateway stores the exact issued challenge: Redis `kasgate:nonce:{nonce}` = PaymentRequired JSON + endpoint slug, EX payment_max_age_seconds.
- PaymentSignature gains `nonce`. The signed tx `payload` MUST equal schemas.payment_payload(nonce) = b"kasgate:v1:" + nonce.
- On the paid retry the gateway loads `required` FROM THE NONCE (never recomputes), checks slug matches, consumes it atomically (GETDEL) only after
  successful settlement. Missing/expired nonce -> 402 `payment_expired` with a fresh PAYMENT-REQUIRED.
- Settlement.payment_nonce is UNIQUE. "Already in mempool/accepted" is success ONLY when the payload nonce is valid and unconsumed.
Pre-lock verification: run engine.verify() (network-free, finalize()-recomputed id, payload, outputs) BEFORE taking kasgate:tx:{txId}.
Settlement finality: settings.settlement_mode "accepted" (default) = submit, then wait until the tx is accepted by the virtual chain
  (subscribe_virtual_chain_changed or poll), up to settlement_timeout_seconds (8 s); timeout -> 503 rpc_unavailable, lock released, nonce kept.
  "mempool" = old behaviour, testnet demos only. Reject any replacement (submit_transaction_replacement is never used by the gateway).
Inputs (attacker-supplied UTXO values): engine fetches each input's real UTXO entry from the node (get_utxos_by_addresses(payerAddress) + mempool) and uses node values/scripts
  for mass and for payer attribution; mismatch -> invalid_payment_header.
Redelivery: same txId + same nonce + same slug, Settlement exists, upstream_status_code is NULL or >= 500, within redelivery_window_seconds and
  delivery_attempts < redelivery_max_attempts -> re-forward upstream, increment delivery_attempts, return PAYMENT-RESPONSE. Otherwise 409.
Transport: PUBLIC_BASE_URL must be https on mainnet (enforced in Settings). SDK keeps pinned fee_to/expected_pay_to options.
Headers: rawTx max 24_000 chars, MAX_HEADER_BYTES 40_960; uvicorn runs with --h11-max-incomplete-event-size 65536.
SSRF: schema rejects any literal IP that is not ip.is_global (covers 100.64.0.0/10, ::1, ULA) and *.localhost/*.internal.
  Runtime guard resolves DNS at request time, pins the resolved IP for the connection, rejects non-global IPs (nip.io, localtest.me), no redirects.
Addresses: validate_kaspa_address now checks the bech32 checksum via kaspa.Address.validate.
Auth (origin binding, single-use challenges, sessions):
- Challenge text = schemas.build_auth_challenge(purpose, domain=host of PUBLIC_BASE_URL, address, nonce, expires_at); purposes AUTH_PURPOSE / REGISTER_PURPOSE.
- AuthChallengeRequest gains purpose "login" | "register". Redis key kasgate:auth:{purpose}:{addr}:{nonce}.
- POST /v1/merchants now REQUIRES challenge + public_key + signature (purpose=register) -> proves address ownership.
- POST /v1/auth/verify now returns SessionIssued{merchant, session_token "kgs_...", expires_at} and DOES NOT rotate api_key.
  Sessions: Redis kasgate:session:{sha256(token)} -> merchant_id, EX session_ttl_seconds. Bearer accepts kg_ (api key) or kgs_ (session).
  Only POST /v1/merchants/me/rotate-key rotates the api key. Web dashboard cookie holds the session_token.
- Challenge rate limit is per-IP only (per-address limit removed: it allowed victim lockout).
Amounts: SompiStr max 18 digits. /healthz stays public but only returns status+network to unauthenticated callers is NOT required for MVP.
Error codes: + payment_expired (402).

## CONTRACT v2.1 — fee floor (2026-11-20)
- Treasury fee = max(ceil(total*150/10000), MIN_OUTPUT_SOMPI). Merchant = total - fee, must be >= MIN_OUTPUT_SOMPI.
- ~~min price 0.4 KAS~~ SUPERSEDED by v2.3: min_price_sompi(floor) = 3*floor = 60_000_000 sompi (0.6 KAS).
- Below 1_333_333_334 sompi the fee is the flat floor (0.2 KAS); above that it is 1.5% (ceil).
- Engine: exact-value checks against PaymentRequired still apply; the ">= 1.5%" check stays valid because fee >= 1.5% always.
- Clients (web lib/sompi.ts, buyer SDK) must replicate: fee = max(ceil(amount*150/10000), min_output_sompi) using DirectoryManifest.min_output_sompi.

## CONTRACT v2.2 — web app auth and session details (2026-11-20)
- Registration and rotate-key return MerchantCreated WITH a session (session_token kgs_ + expires_at), so the web app never stores a kg_ key in a cookie.
- Challenge "Domain:" = urlsplit(PUBLIC_BASE_URL).netloc lowercased (host, plus :port only when the URL has one). Exactly one form; clients compare exact string.
  The web app's public URL that users see must therefore equal PUBLIC_BASE_URL's netloc (in local dev: localhost:8000 vs the web on :3000 → web compares with NEXT_PUBLIC_GATEWAY_URL netloc, which must equal PUBLIC_BASE_URL).
- SompiStr 18-digit cap stands (max 999_999_999_999_999_999 sompi ≫ total KAS supply).
- KasWare signature format: script-signed (kaspa sign_message) registration verified live on tn10; real KasWare 0.11.6 (Chrome) schnorr signMessage verified live on tn10 for register + login (Nov 20, 2026); gateway normalisation (hex128 / Base64 64|65 bytes) is the contract.

## CONTRACT v2.3 — storage-mass correction to the minimum price (2026-11-20, from a live testnet finding)
- At 0.4 KAS the two 0.2 KAS outputs use the entire 100_000 standard storage mass; any change output makes the tx non-standard.
- Merchant output must be >= 2*MIN_OUTPUT_SOMPI. min_price_sompi(floor) = 3*floor = 60_000_000 sompi (0.6 KAS). Fee rule unchanged.
- Verified with kaspa.calculate_storage_mass: at >= 0.6 KAS a single-input payment with change >= ~0.3 KAS stays <= 100_000.
- Buyer SDK MUST select inputs so change is 0 or >= 30_000_000 sompi (add another UTXO when needed); never emit small change.
- Payments drawing from more than 16 payer addresses' UTXOs are rejected (invalid_payment_header).

## CONTRACT v2.4 — proxy, nonce and session details (2026-11-20)
- /v1/quote issues a stored, payable nonce and counts against the unpaid per-IP limit. Every /p response that mints a challenge counts as an unpaid hit.
- kasgate:noncelock:{nonce} NX EX 600 is part of the contract (taken before kasgate:tx:{txId}); the unique payment_nonce index is the backstop.
- Slug mismatch on a paid retry -> 402 invalid_payment_header + fresh challenge (no new code).
- Redelivery: not re-verified on-chain (the Settlement row is the proof); bound to payer, method, path. Query string and body are not bound in the MVP.
- Sessions: Redis set kasgate:sessions:{merchant_id} indexes the merchant's session hashes. DELETE /v1/auth/session [Bearer kgs_] logs out the current session.
  rotate-key revokes ALL sessions of that merchant, then issues the new one returned in MerchantCreated.
- Challenge Domain includes :port when PUBLIC_BASE_URL has one (exact netloc.lower()).
- Registration/login require Redis regardless of RATE_LIMIT_ENABLED.

## CONTRACT v2.5
- Sompi int fields (e.g. EndpointCreate/Read.price_sompi) are capped at MAX_SOMPI = 999_999_999_999_999_999 (18 digits), same as SompiStr. 19 digits -> 422.

## CONTRACT v2.6 — payer proof (closes the mempool front-running finding)
- PaymentSignature gains `payerProof`: 128-hex Schnorr kaspa.sign_message(schemas.payer_proof_message(nonce, txId), payer_private_key)
  where payer_proof_message = "kasgate:v1:{nonce}:{txId}" (Base64 64/65-byte forms normalised to hex like auth signatures).
- payerAddress must be a P2PK Schnorr address (script 0x20 <32-byte x-only pubkey> 0xac). Engine verify(): extract the x-only pubkey from
  pay_to_address_script(payerAddress), kaspa.verify_message(msg, payerProof, PublicKey(xonly_hex)) must be True, else invalid_payment_header.
  resolve_inputs() already requires at least one input to be spent from payerAddress's script, so an observer of the tx cannot claim it.
- Verified with kaspa==2.1.0: PublicKey(xonly).to_address() round-trips and verify_message accepts sign_message output.
- Payers MUST spend P2PK Schnorr UTXOs (kaspa:q... addresses); script-hash (P2SH) and ECDSA payers are refused with invalid_payment_header.
- The proof binds nonce and txId (not method/path); the nonce itself is already bound to the endpoint that issued it.

## CONTRACT v2.8 — one-click OpenAPI import (additive)
POST /v1/endpoints/import [Bearer kg_ or kgs_, same dependency as the other endpoint routes] accepts OpenApiImportRequest (extra="forbid").
mode: "preview" | "create". Exactly one of spec_text or spec_url. upstream_base_url and default_price_sompi are required; optional upstream_headers, category, is_public_listed (default true).
selections: list of {method, path, price_sompi?} (1..500, unique method+path) is required for create and rejected for preview. method is GET|POST|PUT|PATCH|DELETE. price_sompi is an optional per-row override; omitted rows use default_price_sompi. Both prices are Sompi integers and must pass compute_fee_split() (>= 0.6 KAS). Imported rows are KAS-priced (EndpointCreate.price_currency defaults to KAS); USD import is not in this version.
mode=preview -> 200 OpenApiImportPreview (Cache-Control: no-store). Nothing is written. Each OpenApiOperationPreview lists key, method, path, operation_id, summary, path_params, importable/skip_reason, slug, upstream_url, proxy_path, proxy_url, price_sompi.
mode=create -> 201 OpenApiImportCreated{created_count, created:[EndpointRead]}. The route is stateless: create re-reads or re-fetches the document and matches selections by method + path. All selected endpoints are created in one transaction or none are.
Errors: 401 missing or bad auth; 409 slug race (everything rolled back); 413 document over 2 MiB or body over 4.25 MiB; 422 per-row error locations or a readable message for a bad document. Bad input never returns 500.
Mapping: one endpoint per operation, allowed_methods=[METHOD]. Path parameters use the existing suffix routing: GET /pets/{petId} has upstream <base>/pets and is called as /p/<slug>/<petId>. The proxy does not check the suffix against the template, the same as every endpoint today. Slugs are deterministic from operationId or method+path, with -2/-3 on collision against the global slug index. Each row is validated by constructing an EndpointCreate. HEAD, OPTIONS and TRACE, plus unsafe paths, are skipped with a reason.
spec_url is fetched through the existing guarded upstream client (DNS pinned to a public IP). Redirects are followed by hand, at most 3, each re-checked, with a 10 s timeout; the 2 MiB cap is enforced while reading. Remote $ref and $dynamicRef are refused anywhere in the document; nothing is ever fetched for a reference. YAML uses safe_load with a nesting depth cap of 100, an alias cap of 1000, and a 2M-node expanded-size cap. Only OpenAPI 3.0.x and 3.1.x are accepted; Swagger 2.0 and OpenAPI 3.2 are rejected. There is no per-merchant endpoint limit in this version.
Source of truth: apps/gateway/app/schemas.py (OpenApiImport*), app/openapi_import.py, app/api_routes.py::import_openapi. Narrative detail: docs/OPENAPI_IMPORT.md.
Additive note (USD import): OpenApiImportRequest gains optional default_price_currency (KAS default) and default_price_usd_micros. A selection may include price_usd_micros. Exactly one price per currency: KAS imports send default_price_sompi and optional per-row price_sompi (each must pass compute_fee_split, >= 0.6 KAS) and omit USD fields; USD imports send default_price_usd_micros and optional per-row price_usd_micros (UsdMicros, 1 USD = 1_000_000 micros) and omit sompi fields. Preview rows and the preview envelope include price_currency, price_sompi (null on USD) and price_usd_micros (null on KAS). Created EndpointRead rows set price_currency and the matching price field, with the other null, satisfying ck_endpoints_price_matches_currency. Mixed or missing prices are 422 at their field location, e.g. ["body","selections",2,"price_sompi"].

## CONTRACT v2.9 — k402 kaspa-utxo ingest (additive)
Source: kaspa-402/k402 commit 63e1eae (PROTOCOL.md "v0.2", k402/schemes.py, k402/wallet.py HotWallet.pay). Research: K402_DIFF.md.
- Every 402 from /p/{slug} (and every fresh-challenge 402) is ALSO a k402 offer body: `k402: "0.2"`, `accepts: [<kaspa-exact-v1 PaymentRequired, same as the header>, <K402UtxoOffer>]`. k402 clients skip the unknown `kaspa-exact-v1` entry; KasGate clients keep reading PAYMENT-REQUIRED. GET /v1/quote/{slug} stays v1-only.
- K402UtxoOffer{scheme:"kaspa-utxo", network:"testnet-10"|"mainnet" (k402 wire names, never the kaspa: CAIP form; anything else is refused), amount_sompi:str (MERCHANT output only), pay_to (merchant address), payment_id:"p_"+16 hex, expires: unix seconds (= the v1 expiresAt), description (endpoint name), facilitator_fee{sompi:str, to: treasury, by:"kasgate"}}. `finality` is omitted (= 1, accepted).
- Quote: total = locked v1 total + tag, where the locked v1 total is PaymentRequired.amount of the challenge minted in the same 402 (KAS-priced: price_sompi; USD-priced: the same single oracle quote, ceil conversion and 0.6 KAS floor as v1, never re-quoted), tag uniform in [0, 1_000_000) sompi (< 0.01 KAS, paid to the merchant); fee = compute_fee_split(total).fee_sompi (max(ceil(1.5 %), 0.2 KAS floor)), amount_sompi = total - fee, total >= 0.6 KAS. The tag exists because k402 txs carry no payload nonce or payerProof: exact amounts are the only on-chain binding, so a bystander's own offer for the same endpoint matches a victim's tx with probability ~ (their open offers) / 1_000_000. The tag is the k402 anti-front-running measure.
- USD-priced endpoints: the k402 offer reuses the v1 challenge's locked quote, so the offer's total minus its tag equals the v1 amount exactly, and the settlement's USD value uses the same locked kasUsdRate. Oracle unavailable -> 503 price_unavailable exactly like v1, with no k402 offer and no kasgate:k402 key written.
- Redis: kasgate:k402:{payment_id} -> JSON{slug, nonce (internal 32 hex, never sent; becomes settlements.payment_nonce), offer, kasUsdRate (the locked rate string for USD-priced endpoints, else null)}, EX payment_max_age_seconds. Paying the v1 challenge and the k402 offer of one 402 are independent payments.
- Retry header: `X-K402-Payment: kaspa-utxo <txid 64 hex> <payment_id>` (exactly three tokens, <= 256 chars). kaspa-session, kaspa-channel and every other scheme are out of scope and get 402 invalid_payment_header. Sending it together with PAYMENT-SIGNATURE is 402 invalid_payment_header. X-K402-Payment is never forwarded upstream.
- Order: parse (bad/empty -> 402 invalid_payment_header + fresh offers) -> load offer -> existing settlement for the txid (either binding) or payment_id -> redelivery (same txid + payment_id + slug + method + path, v1 window and cap) else 409 -> unknown/expired offer -> 402 payment_expired -> other slug -> 402 invalid_payment_header -> `SET kasgate:k402lock:{payment_id} NX EX 600` then the SHARED `SET kasgate:tx:{txId} NX EX 600` (held -> 409 payment_replayed) -> engine.verify_k402 -> settle + deliver exactly as v1, then GETDEL the offer. Only a verification failure releases both locks.
- engine.verify_k402(tx_id, offer): nothing is submitted (the payer already did). accepted mode reads the sink FIRST. Lookup: get_mempool_entries_by_addresses([merchant, treasury]) receiving side (full tx) -> outputs checked, then the virtual chain is polled from that sink until it accepts the txid (timeout -> one UTXO-index check -> else payment_not_found); not in the mempool -> get_utxos_by_addresses([merchant, treasury]) filtered by txid (accepted outputs only). Nothing found -> 402 payment_not_found (k402 clients retry the same header on 402, ~5 times over ~15 s).
- Output rule (check_k402_outputs), by index AND by locking script: outputs[0] = pay_to EXACTLY amount_sompi, outputs[1] = facilitator_fee.to EXACTLY facilitator_fee.sompi, both re-checked against the fee floor and the 2*floor merchant minimum. Treasury output missing, 1 sompi short or over, paying another address, or found at any index other than 1 (swap, reordering) -> invalid_fee_split; merchant short -> underpaid; merchant over, wrong script or at another index -> invalid_fee_split. An output that is no longer visible (spent before the lookup) is refused, never assumed. The kasgate:v1 payload and payerProof are NOT required (official clients send an empty payload); the official k402 server's balance-delta check is not used.
- settlements: payment_scheme "kaspa-exact-v1"|"k402-kaspa-utxo" (server default v1), k402_payment_id (unique index ix_settlements_k402_payment_id, "p_"+16 hex, set iff k402), payer_address NULL only for k402 (no payer proof). Alembic 0004_k402_utxo (down_revision 0003_usd_pricing); its downgrade refuses while k402 rows exist. SettlementRead gains payment_scheme; payer_address and TaxReportRow.payer_address are nullable.
- Residual vs v1: no payer identity, so the payment_id (sent only to the client that asked for the offer) is the bearer secret for a paid k402 call, and front-running protection is the amount tag above rather than payerProof.
- Verified offline with kaspa==2.1.0: create_transactions(outputs=[merchant, treasury]) keeps that order and appends change, also with a larger output 1 and with 68+ inputs; payload is empty. Upstream finding: HotWallet.__init__ calls to_address("testnet-10"), which kaspa 2.1.0 refuses ("Invalid network type"), so an unmodified HotWallet cannot be constructed on testnet-10 (mainnet is fine; create_transactions itself needs "testnet-10"). The unmodified HotWallet.pay + k402.Client flow is covered in tests/test_k402.py with the wallet assembled field by field.

## CONTRACT v2.10 — community kaspa-x402 `exact` / `kaspa-exact-v2` (standard-native) ingest
Source: elldeeone/kaspa-x402 tag v1.0.1 (commit 56221913531bcb8367a900d28ed24c62d50591a1): protocol/spec (http-profile, exact binding), packages/core (envelope narrowing, canonical JSON, request hash, exact-authorization), packages/server (`#verifyStandardNative`). Research: SPEC_DIFF.md. Out of scope: batch-settlement, the additive and hash-chain exact profiles (their entries are never offered; a payload naming them is 402 invalid_payment_header).
- **No platform fee on this binding during the beta.** The exact entry pays `payTo` = the merchant the full price; there is no treasury output, `fee_amount_sompi` is 0. kaspa-exact-v1 and k402 are unchanged (output 0 merchant, output 1 treasury; a v1 tx without output 1 is never approved).
- PAYMENT-REQUIRED (every fresh-challenge 402) is ONE x402 v2 envelope, canonical JSON (sorted keys, compact) then standard Base64: `{x402Version: 2, resource: {url, description}, accepts: [<exact entry>, <kaspa-exact-v1 terms>], extensions: {"payment-identifier": {info: {required: true}, schema}}, error}` plus the kaspa-exact-v1 terms mirrored at the top level (`scheme, network, asset, amount, payTo, platformFee, nonce, expiresAt[, extra]`). The `kaspa-exact-v1` entry is the v1 PaymentRequired without `x402Version`. Official clients validate each accepts entry and skip the ones they do not support (core `narrowPaymentRequiredEnvelope`), so they select the exact entry; KasGate SDK >= this release selects the kaspa-exact-v1 entry; the mirror keeps lenient readers of the flat header working. Deviation, documented: the kaspa-x402 HTTP profile says Kaspa servers "must emit only exact and batch-settlement entries"; KasGate also emits its own kaspa-exact-v1 entry, which conforming clients skip. A v1 verification failure on a known nonce still answers with the flat v1 header (same terms, no new offers). Header size stays under MAX_HEADER_BYTES (40,960).
- Exact entry: `{scheme: "exact", network: "kaspa:testnet-10"|"kaspa:mainnet", amount, asset: "KAS", payTo, maxTimeoutSeconds: payment_max_age_seconds, extra: {binding: "kaspa-exact-v2", profile: "standard-native", paymentFlow: "upfront", finality: "accepted", transactionEncoding: "kaspa-sdk-safe-json-v2.0.0", payToScriptPublicKey}}`. `resource.url` = PUBLIC_BASE_URL + the raw request path + raw query (what a WHATWG client has as `href` without fragment). `amount` = the v1 challenge's LOCKED total from the same 402 (KAS-priced: price_sompi; USD-priced: the same single oracle quote, ceil conversion and 0.6 KAS floor). Oracle unavailable -> 503 price_unavailable with no header, no accepts and no kasgate:exact key, exactly like v1 and k402.
- KasGate policy: minimum merchant output 20,000,000 sompi (0.2 KAS; below it no exact entry is offered — unreachable while the v1 minimum price is 0.6 KAS). Signatures must be SIGHASH_ALL (0x01) and the transaction mass standard; miner fee <= 1 KAS (the official MAX_SAFE_TRANSACTION_FEE_SOMPI).
- 402 body (k402 shape kept): `k402: "0.2"`, `accepts: [<v1 PaymentRequired>, <K402UtxoOffer>, <exact entry>]`. The exact entry is appended, nothing is replaced; k402 and KasGate clients skip it.
- Redis: `kasgate:exact:{slug}:{paymentRequirementsHash}` -> canonical JSON{slug, requirement, kasUsdRate (locked rate for USD endpoints, else null)}, EX payment_max_age_seconds. The offer is not consumed on settlement (a KAS-priced offer is shared by every 402 at that price); the unique payment identifier, txId and request hash make each settlement single-use. `kasgate:pid:{payment identifier}` NX EX 600 is the identifier claim.
- Retry: PAYMENT-SIGNATURE = Base64(canonical JSON PaymentPayload) `{x402Version: 2, accepted, payload: {type: "exact-transaction", profile: "standard-native", transaction (safe-JSON artifact), transactionEncoding, paymentOutputIndex, requestHash, payerAddress?, authorization: {version: "kaspa-x402-exact-request-authorization-v2", inputIndex, expiresAt, digest, signature}}, extensions: {"payment-identifier": {info: {required: true, id}}}}`, <= 65,536 chars. Dispatch: a PAYMENT-SIGNATURE whose decoded JSON has `accepted` or `payload` takes the exact path, anything else the v1 path; X-K402-Payment is checked first and combining it with PAYMENT-SIGNATURE stays 402 invalid_payment_header.
- Order: strict parse (bad -> 402 invalid_payment_header + fresh offers) -> prepare the upstream request -> load the stored offer for `accepted` -> requestHash = sha256(stableStringify({method, url: resource URL, body: UTF-8 text or null, paymentRequirementsHash})) -> pure verification without expiry (artifact, txid recomputation, outputs, mass, input Schnorr signatures, authorization digest + signature) -> existing settlement for the txId (any binding) or payment identifier: redelivery when the identifier, txId, requestHash, payer, slug, method and path all match (v1 window and attempt cap, re-verified in full), else 409 payment_replayed (`kaspa_payment_identifier_conflict` when the identifier was used for another request) -> no live offer -> 402 payment_expired (`invalid_kaspa_x402_accepted`) -> authorization expiry (`expiresAt` in the future, <= now + maxTimeoutSeconds) -> `SET kasgate:pid:{id} NX` then the SHARED `SET kasgate:tx:{txId} NX` (one txId can never be claimed through two bindings) -> node lookup of every embedded UTXO (confirmed or mempool, same amount and script) -> submit and wait for ACCEPTANCE regardless of settlement_mode -> settlement row -> forward. Failures before the lock -> 402 with fresh offers; after it the locks are released; node down -> 503 rpc_unavailable + Retry-After 5.
- Error codes: invalid_exact_payment (envelope, signatures, authorization, request hash, unknown UTXOs), underpaid (payment output short), tx_rejected (fee ceiling, outputs > inputs, mass, node rejection), wrong_network, payment_expired, invalid_payment_header, payment_replayed. Messages embed the official reason where one exists (invalid_kaspa_x402_accepted, missing_kaspa_payment_identifier, expired_authorization, authorization_exceeds_max_timeout).
- PAYMENT-RESPONSE: the official SettlementResponse, canonical JSON + Base64: `{success: true, transaction: txId, network, payer, amount, extensions: {kaspa: {exactProfile: "standard-native", paymentOutputIndex, finality: "accepted", requestHash, transactionEncoding}, kasgate: {platformFeeSompi: "0", usdValueAtSettlement}}}`. Redeliveries carry the same receipt.
- settlements: payment_scheme "kaspa-exact-v2" (with v1 and k402 in ck_settlements_payment_scheme_known), payment_identifier (unique index ix_settlements_payment_identifier, `^[A-Za-z0-9_-]{16,128}$`), request_hash (64 lowercase hex); both set iff kaspa-exact-v2. treasury_address and payment_nonce become nullable: NULL exactly on kaspa-exact-v2 rows, which also have fee_amount_sompi = 0, a payer_address and no k402_payment_id (ck_settlements_exact_v2_shape); every other row keeps fee > 0 with a treasury and a nonce (ck_settlements_treasury_split_unless_exact_v2). tx_id and payment_nonce unique indexes unchanged. Alembic 0005_exact_v2 (down_revision 0004_k402_utxo); its downgrade refuses while kaspa-exact-v2 rows exist. SettlementRead: payment_scheme gains "kaspa-exact-v2", treasury_address and payment_nonce nullable, + payment_identifier.
- Interop evidence: the official vectors (tests/fixtures/kaspa-x402, MIT, hashes in its README) and tests/test_interop_kaspa_x402.py, where the npm-published @kaspa-x402/client 1.0.1 parses a real KasGate 402, selects the exact entry, computes the same paymentRequirementsHash and requestHash, pays and accepts the PAYMENT-RESPONSE with `applySettlement`. GET /v1/quote/{slug} and the agent catalog stay kaspa-exact-v1 only.

## CONTRACT v2.11 — prepaid credit (`kasgate-prepaid-v1`, additive)
Design: x402v2/PREPAID_DESIGN.md option (a1). A buyer deposits once on-chain at a merchant, then pays calls with signed, single-use debits. KasGate never holds coins: the deposit pays the merchant (output 0) and the treasury (output 1) on-chain exactly like a v1 payment; the balance is a ledger of what the merchant still owes in calls. Unused credit is a merchant obligation, never a KasGate liability, and there is no withdrawal route.
- **Deposit = a v1 split payment.** `POST /v1/prepaid/deposits/quote` (public, unpaid rate limit; strict body `{slug, payer_address, amount_sompi:int}`, extra fields and string numbers are 422) -> 201 PrepaidDepositQuote `{slug, merchant_id, payer_address, deposit_sompi, fee_sompi, credit_sompi, required: PaymentRequired, deposit_url}` (no `balance_sompi`: this response is unsigned, see v2.12.2). `amount_sompi` is the deposit TOTAL; it must pass `compute_fee_split` (>= 0.6 KAS, fee = max(ceil(1.5 %), 0.2 KAS)). credit = merchant share (output 0) only; the treasury fee (output 1) is never credited. `payer_address` must be a P2PK Schnorr address (its x-only key owns the balance), else 400 `invalid_payment_header` (same rule on `/challenge`). A deposit that would take the balance above `PREPAID_MAX_BALANCE_SOMPI` (default 100,000 KAS, >= 0.6 KAS) is 422 `prepaid_cap_exceeded` at quote time, by the same rule `POST /v1/prepaid/deposits` enforces (balance + in-flight debits + credit > cap, one shared helper; see v2.12.1 and v2.12.2).
- `POST /v1/prepaid/deposits` with `PAYMENT-SIGNATURE` (v2.6 payer proof required, `payerAddress` must equal the quoted payer) -> 201 PrepaidDepositReceipt `{deposit_id, tx_id, slug, merchant_id, payer_address, deposit_sompi, fee_sompi, credit_sompi, created_at}` + `PAYMENT-RESPONSE` (no `balance_sompi`: unsigned, see v2.12.2). Order mirrors the v1 proxy: parse -> load `kasgate:prepaid:deposit:{nonce}` (unknown/expired -> 402 `payment_expired`) -> existing settlement for the txId (same tx + nonce + payer -> **200** with the same receipt, idempotent; anything else -> 409 `payment_replayed`) -> merchant payout address unchanged since the quote (else 402 `payment_expired`) -> pure `engine.verify` -> `SET kasgate:noncelock:{nonce} NX` then the SHARED `SET kasgate:tx:{txId} NX` (either held -> 409) -> `resolve_inputs` + `settle` -> ONE DB transaction: settlement row (kaspa-exact-v1, fee > 0, treasury), balance upsert, `prepaid_deposits` row. A deposit challenge lives in its own Redis namespace, so it can never pay a `/p` call, and a `/p` challenge can never fund a deposit; a txId used for one can never be used for the other (shared `kasgate:tx:{txId}` lock + unique `settlements.tx_id` + unique `prepaid_deposits.tx_id`).
- **Running balance.** One row per (merchant, buyer x-only key): `balance = deposited - debited`, `balance >= 0` (DB CHECKs). Deposits by the same key at the same merchant add up; credit is not portable across merchants.
- **Debit challenge.** `POST /v1/prepaid/challenge` (public, unpaid rate limit; strict body `{slug, payer_address, method, path, body_hash}`) -> 201 PrepaidChallenge `{nonce, message, slug, merchant_id, payer_address, method, path, body_hash, amount_sompi, kas_usd_rate, balance_sompi, expires_at}`. `path` is the exact proxy path incl. query (`/p/{slug}`, `/p/{slug}/...` or `/p/{slug}?...`, printable ASCII, no `#`, <= 2048 chars). `body_hash` = SHA-256 hex of the raw body or `-` for none. Method not allowed -> 405; balance < price -> 402 `insufficient_balance` (body = the prepaid-only 402 below; nothing stored). USD-priced endpoints: the price is the unfloored ceil conversion at one oracle quote, locked into the challenge (`kas_usd_rate`). Stored as `kasgate:prepaid:challenge:{nonce}`, EX `payment_max_age_seconds`.
- **Message** (deviation from the design doc: no `Deposit:` line, because the balance is a running balance, not per-deposit buckets):
  ```
  KasGate
  Domain: {netloc of PUBLIC_BASE_URL}
  Purpose: kasgate:v1:prepaid-debit
  Address: {payer_address}
  Merchant: {merchant_id}
  Method: {METHOD}
  Path: {path + ?query, raw}
  Body-Hash: {sha256 hex | -}
  Amount: {sompi}
  Nonce: {32 hex}
  Expires: {expires_at.isoformat(), e.g. 2026-11-26T10:00:00+00:00}
  ```
  Signed with kaspa `sign_message` (Schnorr) by the depositing key. Clients must rebuild this text from their own request and refuse to sign anything else (the Python SDK does).
- **Paying a call.** Send `X-KasGate-Prepaid: Base64(JSON{nonce, signature})` (128-hex or Base64 64-byte signature, header <= 512 chars) on the `/p/{slug}` request. Order: parse (bad -> 402 `invalid_payment_header`) -> request size/shape checks -> nonce already in `prepaid_debits` -> 409 `payment_replayed` -> challenge unknown/expired -> 402 `payment_expired` -> the stored challenge must match the request actually served (endpoint, merchant, method, raw path + query, body hash; never client copies) and the signature must verify under the stored x-only key, else 402 `invalid_payment_header` -> `SET kasgate:prepaid:noncelock:{nonce} NX` (held -> 409) -> ONE transaction: conditional `UPDATE ... SET balance = balance - amount WHERE balance >= amount` + `prepaid_debits` insert (unique nonce) -> 0 rows -> 402 `insufficient_balance`, nothing debited -> consume the challenge -> forward upstream. Concurrent debits can never overdraw and a replay debits at most once.
- **Receipt and refunds.** Every forwarded call carries `X-KasGate-Prepaid-Receipt: Base64(JSON{debitId, nonce, amountSompi, balanceSompi, status: "debited"|"refunded"})`. No upstream response -> 502 `upstream_error` and the debit is refunded; upstream 5xx -> the upstream response, refunded; 2xx-4xx stay debited (`upstream_status_code` is recorded). A refund that cannot be written is pushed to `kasgate:deadletter:prepaid-refunds` and the receipt says `debited`. A debit nonce is single-use: retrying after a refund needs a new challenge (no cached redelivery).
- **Headers.** `X-KasGate-Prepaid` and `X-KasGate-Prepaid-Receipt` are in PAYMENT_HEADERS: stripped from the request before forwarding and from upstream responses. Sending `X-KasGate-Prepaid` together with `PAYMENT-SIGNATURE` (v1 or `exact`) or `X-K402-Payment` -> 402 `invalid_payment_header`. A request carrying a prepaid header is not counted against the unpaid rate limit.
- **Prepaid-only endpoints.** `endpoints.prepaid_only` (default false). When true, a KAS price may be any positive sompi amount below the 0.6 KAS floor; when false the v2.3 floor still applies (create/update -> 422 "set prepaid_only=true"). Their 402 (on `/p`, `/v1/quote/{slug}` and `insufficient_balance`) has `accepts: [PrepaidOffer]` only: no PAYMENT-REQUIRED header, no nonce minted, `k402: null`, no k402 or `exact` offer; on-chain payment headers sent to them -> 402 `invalid_payment_header` without touching the engine. Other endpoints keep their v1 402 unchanged and accept prepaid debits as well.
- **PrepaidOffer** `{scheme:"kasgate-prepaid-v1", network, asset:"KAS", amount (per-call debit, sompi), payTo, merchantId, prepaidOnly, minDepositSompi, depositQuoteUrl, depositUrl, challengeUrl, balanceUrl}`.
- **Discovery.** Catalog `schemes`: `["kasgate-prepaid-v1"]` when prepaid-only, else `["kaspa-exact-v1", "kasgate-prepaid-v1"]`; catalog items and `/v1/directory` entries carry `prepaid_only`.
- **Reads.** `GET /v1/prepaid/balance?slug=&payer_address=` (public for `spendable_sompi` / `expires_at` only; everything else, including `balance_sompi`, only when buyer-signed, see v2.12.1). `GET /v1/prepaid/balances|deposits|debits?limit=&offset=` [Bearer] -> the merchant's own rows, newest first.
- **Storage (Alembic 0006_prepaid).** `endpoints.prepaid_only`; `prepaid_balances` (unique (merchant_id, payer_public_key), index payer_address, CHECKs balance >= 0, totals >= 0, balance = deposited - debited, key = 64 hex); `prepaid_deposits` (unique `ix_prepaid_deposits_tx_id` and settlement_id, FKs to balance/merchant/settlement, CHECK credit + fee = deposit, both > 0); `prepaid_debits` (unique nonce, indexes on balance, (merchant, created_at), (endpoint, created_at); CHECK status in (debited, refunded) and refunded_at iff refunded). Slug lookups use the existing unique `ix_endpoints_slug`. Downgrade below 0006 refuses while any prepaid row or prepaid-only endpoint exists.
- **Errors.** New code `insufficient_balance` (402); v2.12.1 adds `prepaid_cap_exceeded` (422) and `invalid_balance_signature` (401). Redis keys: `kasgate:prepaid:deposit:{nonce}`, `kasgate:prepaid:challenge:{nonce}`, `kasgate:prepaid:noncelock:{nonce}`, `kasgate:deadletter:prepaid-refunds`; deposits also use `kasgate:noncelock:{nonce}` and the shared `kasgate:tx:{txId}`.
- **Policy not built in v2.11:** credit TTL/expiry and merchant refund tooling for unused balances (design doc open question 2); the public balance read reveals a buyer's *spendable* credit at a merchant to anyone who knows the address (by design, v2.12.1; `balance_sompi`, identity, `updated_at` and the ledger totals are hidden).

## CONTRACT v2.12 — free trial calls (`kasgate-trial-v1`) and merchant webhooks (additive)

Design notes: [TRIALS_WEBHOOKS.md](TRIALS_WEBHOOKS.md). Paid calls are unchanged: outputs, the fee `max(1.5 %, 0.2 KAS)` and the 0.6 KAS minimum apply exactly as before; trial calls move no coins and never carry a fee.

### Free trial calls
- **Merchant settings.** `endpoints.free_trial_calls` (strict int 0..100, default 0 = no trial) and `endpoints.trial_daily_cap` (strict int 1..100000, default 100: trial calls served per UTC day across all buyers). Both are on EndpointCreate/Update/Read; on update they may be omitted but not null (422). `POST /v1/endpoints/import` takes `free_trial_calls` for every imported endpoint. Strings, floats and booleans are 422.
- **Offer.** A 402 from an endpoint with `free_trial_calls > 0` (on-chain 402 and the prepaid-only 402) carries `X-KasGate-Trial-Offer: Base64(JSON{scheme:"kasgate-trial-v1", freeTrialCalls, challengeUrl, statusUrl})`. The same object is also present as the additive JSON field `trial` on that 402 body (absent when the endpoint has no trial), so JSON-only clients do not have to read the header. Catalog `schemes` gain `"kasgate-trial-v1"`; catalog items and `/v1/directory` entries carry `free_trial_calls`.
- **Challenge.** `POST /v1/trials/challenge` (public, unpaid rate limit; strict body `{slug, payer_address, method, path, body_hash}`, same field rules as the v2.11 debit challenge) -> 201 TrialChallenge `{nonce, message, slug, merchant_id, payer_address, method, path, body_hash, free_trial_calls, calls_used, remaining, expires_at}`. `payer_address` must be P2PK (its x-only key is the buyer identity), else 400 `invalid_payment_header`. Unknown slug 404; method not allowed 405; no trial, key used up, or daily cap reached -> 402 `trial_exhausted` (no `accepts`: pay the 402 already in hand). Stored as `kasgate:trial:challenge:{nonce}`, EX `payment_max_age_seconds`. The text to sign:
  ```
  KasGate
  Domain: <gateway host>
  Purpose: kasgate:v1:trial-call
  Address: <payer_address>
  Merchant: <merchant uuid>
  Endpoint: <slug>
  Method: <METHOD>
  Path: </p/... incl. query>
  Body-Hash: <sha256 hex | ->
  Nonce: <32 hex>
  Expires: <ISO-8601 UTC>
  ```
  It carries no amount and its Purpose differs from the prepaid debit, payer proof and login texts, so no other signature can stand in for it (and it can never move coins).
- **Using a trial.** Send `X-KasGate-Trial: Base64(JSON{nonce, signature})` on the `/p/{slug}` request. Order: parse (bad -> 402 `invalid_payment_header`) -> request size/shape checks -> per-IP trial limit (`RL_TRIAL_CALLS_PER_IP_PER_HOUR`, default 30; 429) -> nonce already in `trial_calls` -> 409 `payment_replayed` -> challenge unknown/expired -> 402 `payment_expired` -> the stored challenge must match the request actually served (endpoint, merchant, method, raw path + query, body hash) and the signature must verify under the stored x-only key, else 402 `invalid_payment_header` -> `SET kasgate:trial:noncelock:{nonce} NX` (held -> 409) -> ONE transaction: `trial_usages` row (insert-if-absent) + conditional `UPDATE ... calls_used = calls_used + 1 WHERE calls_used < free_trial_calls`, conditional daily upsert `... calls = calls + 1 WHERE calls < trial_daily_cap`, `trial_calls` insert (unique nonce), `trial.used` outbox event -> either conditional write hitting 0 rows rolls everything back -> 402 `trial_exhausted` -> consume the challenge -> forward upstream. Concurrent trial calls can never exceed either limit (row locks in Postgres; Redis only guards the nonce).
- **Failures answer with the normal 402.** Every 402 on a trial call (`invalid_payment_header`, `payment_expired`, `trial_exhausted`) is the endpoint's ordinary 402 (fresh on-chain challenge with `PAYMENT-REQUIRED`, or the prepaid-only offer), so the buyer can pay straight away. `trial_exhausted` adds `X-KasGate-Trial-Remaining: 0` and drops the trial offer.
- **Receipt and refunds.** Every forwarded trial call carries `X-KasGate-Trial-Limit`, `X-KasGate-Trial-Remaining` and `X-KasGate-Trial-Receipt: Base64(JSON{trialCallId, nonce, limit, remaining, status:"used"|"refunded"})`. No upstream response -> 502 `upstream_error`, upstream 5xx -> the upstream response; both give the call back to the key (`status` `refunded`). The endpoint's daily counter is not given back. A refund that cannot be written goes to `kasgate:deadletter:trial-refunds` and the receipt says `used`.
- **Headers.** All five trial headers are in PAYMENT_HEADERS (stripped both ways). `X-KasGate-Trial` together with `PAYMENT-SIGNATURE`, `X-K402-Payment` or `X-KasGate-Prepaid` -> 402 `invalid_payment_header`. A request carrying the trial header is not counted against the unpaid rate limit (it has its own).
- **Reads.** `GET /v1/trials/status?slug=&payer_address=` (public, unpaid rate limit) -> TrialStatusRead `{slug, merchant_id, payer_address, free_trial_calls, calls_used, remaining}` (`remaining` is 0 while the daily cap is reached). `GET /v1/trials/calls?limit=&offset=` [Bearer] -> the merchant's TrialCallRead rows, newest first.
- **Error code.** New `trial_exhausted` (402).

### Merchant webhooks
- **Routes** (all [Bearer], merchant-scoped; another merchant's ids are 404): `GET /v1/webhooks/event-types`; `POST /v1/webhooks` (strict `{url, event_types[1..6], description?<=200}`) -> 201 WebhookCreated `{webhook: WebhookRead, secret}`; `GET /v1/webhooks`; `GET|PATCH|DELETE /v1/webhooks/{id}` (PATCH `{url?, event_types?, description?, is_active?}`, nulls for url/event_types/is_active are 422; DELETE 204 removes its deliveries); `POST /v1/webhooks/{id}/rotate-secret` -> WebhookCreated with a new secret; `POST /v1/webhooks/{id}/test` -> queues a `webhook.test` event for this webhook only, attempts it once immediately and returns the WebhookDeliveryRead (retries then follow the normal schedule); `GET /v1/webhooks/{id}/deliveries?status=&limit=&offset=`; `POST /v1/webhooks/{id}/deliveries/{delivery_id}/redeliver` -> 202, status `pending`, attempts 0, due now, same event id and body (409 while an attempt is in flight). At most `WEBHOOK_MAX_PER_MERCHANT` (10) webhooks per merchant (409).
- **Event types:** `payment.settled` (every settled `/p` payment: kaspa-exact-v1, k402 and `exact`; data: settlement_id, tx_id, payment_scheme, network, endpoint_id/slug, payer/merchant address, amount/merchant_amount/fee in sompi strings, kas_usd_rate, usd_value, request method/path, settled_at), `prepaid.deposit` (deposit_id, settlement_id, tx_id, endpoint_slug, payer_address, deposit/fee/credit/balance sompi), `prepaid.debit` (debit_id, endpoint, payer, amount, balance, kas_usd_rate, request), `trial.used` (trial_call_id, endpoint, payer_address, calls_used, free_trial_calls, remaining, request), `endpoint.created` / `endpoint.updated` (endpoint fields incl. prices, methods, flags, free_trial_calls; updated adds `changed_fields`; deactivation is an `endpoint.updated` with `is_active:false`). `webhook.test` is sent only by the test route. Sompi amounts are decimal strings.
- **URL rules.** HTTPS only, <= 2048 printable ASCII, no credentials or fragment, no `localhost`/`.local`/`.internal`/`.lan`/`.home.arpa`/`.localdomain` names or single-label hosts, no non-global IP literals (422). At delivery time the name is resolved again by the upstream SSRF guard: every resolved address must be global (v4-mapped, 6to4, Teredo, NAT64 and SIIT embeddings included; the whole SIIT `0:0:0:0:ffff:0:0:0/96` prefix is refused) and the socket connects to the validated IP; no redirects (3xx is a failed attempt), no proxy env, 10 s total timeout, request body <= 64 KiB, at most 64 KiB of the response is read.
- **Envelope** (the POST body, compact JSON with sorted keys): `{id: "evt_<32 hex>", type, api_version: "2.12", created_at, merchant_id, data}`. Headers: `Content-Type: application/json`, `User-Agent: KasGate-Webhooks/2.12`, `X-KasGate-Event-Id`, `X-KasGate-Event-Type`, `X-KasGate-Delivery-Id`, `X-KasGate-Timestamp: <unix seconds>`, `X-KasGate-Signature: t=<unix>,v1=<hex HMAC-SHA256(secret, "<t>.<raw body>")>`. Receivers verify the raw body, refuse timestamps more than 300 s from their clock, and dedupe on the event id (the same id is used for every retry and redelivery; event ids of sourced events are deterministic `sha256(type:source)`, so an event is written once).
- **Secrets.** `whsec_` + 43 url-safe chars, returned only by create and rotate-secret, stored Fernet-encrypted (`ENCRYPTION_KEY`), never logged; reads expose `secret_prefix` (first 10 chars). Rotation keeps the replaced secret signing for 24 h (v2.12.1).
- **Outbox.** Events and their deliveries are written by `enqueue_event` inside a SAVEPOINT of the same transaction as the settlement / deposit / debit / trial / endpoint row, after that row is flushed; any outbox error rolls back only the savepoint and is logged, so webhooks can never fail or block a payment. The dispatcher (app lifespan, `WEBHOOK_DISPATCHER_ENABLED`) polls every 2 s, claims up to 20 due deliveries with `FOR UPDATE SKIP LOCKED` (status `delivering`, attempts + 1, 60 s lease) and sends up to 8 at once. 2xx -> `succeeded`; anything else -> `pending` with `next_attempt_at = now + min(30 s x 2^(attempts-1), 3600 s) x jitter(0.9..1.1)`; after 8 attempts, or when the webhook is disabled or its secret cannot be decrypted -> `dead`. An expired lease is reclaimed by the next pass; a result is written only by the lease holder (same attempts count, still `delivering`).
- **Storage (Alembic 0007_trials_webhooks).** `endpoints.free_trial_calls` / `trial_daily_cap` with CHECKs; `trial_usages` (unique (endpoint_id, payer_public_key), index merchant_id, CHECKs calls_used >= 0, key = 64 hex); `trial_daily_counts` (PK (endpoint_id, day), CHECK calls >= 0); `trial_calls` (unique nonce, indexes usage_id, (endpoint_id, created_at), (merchant_id, created_at); CHECK status in (used, refunded) and refunded_at iff refunded); `webhooks` (index merchant_id, CHECK https URL and non-empty event_types); `webhook_events` (unique `event_id` matching `^evt_[0-9a-f]{32}$`, index (merchant_id, created_at), CHECK known type); `webhook_deliveries` (unique (event_pk, webhook_id), indexes (webhook_id, created_at) and (merchant_id, created_at), partial due-index on next_attempt_at WHERE status in (pending, delivering), CHECKs on status, attempts >= 0 and delivered_at iff succeeded). No new `tx_id` or `slug` columns (existing unique indexes stay). Downgrade below 0007 refuses while any trial call, trial-enabled endpoint or webhook exists.
- **Not built in v2.12:** Sybil resistance beyond the per-IP limit and the daily cap (a fresh key is free to make); retention pruning of `webhook_events` / `trial_calls` (test events excepted, v2.12.1); per-delivery manual payload inspection in the dashboard.

## CONTRACT v2.12.1 — security fixes on prepaid, trials and webhooks (05 red-team pass on 4d39527)
No migration (main stays at 0007). Additive except where marked **behaviour change**.

- **Prepaid balance cap at deposit time (M1, behaviour change).** `prepaid_max_balance_sompi` (setting, default 10_000_000_000_000 sompi = 100 000 KAS) is the most one buyer key may hold at one merchant. It is checked at `POST /v1/prepaid/deposits/quote` as before and now again in `POST /v1/prepaid/deposits`, after the Redis nonce/tx locks and BEFORE `resolve_inputs`/`settle`: the `(merchant_id, payer_public_key)` row of `prepaid_balances` is created if missing (ON CONFLICT DO NOTHING) and locked `SELECT ... FOR UPDATE` for the rest of the deposit transaction, so deposits for one key serialize. The cap setting is read *after* that lock (and after overdue credit is expired), so a cap lowered while a deposit was queued is a 422 rather than a settled-then-DLQ 503. The cap is on `balance_sompi` plus any *in-flight* prepaid debit (a `prepaid_debits` row with `status = 'debited'` and `upstream_status_code` IS NULL: the amount is already subtracted from the balance, but a 5xx or unanswered upstream will refund it). An open refund hold still counts in `balance_sompi`; a paid refund or an expiry lowers it and frees room. Overdue credit is expired under that same row lock *before* the cap is checked (and again just before the credit is applied, so an expiry that matured during settle is not credited on top of). `balance + in-flight + credit > cap` -> **422 `prepaid_cap_exceeded`** (`{error, message}`), the transaction is never submitted and the payment locks are released (the quote's nonce stays unconsumed until it expires, so the same signed payment can be retried after a debit, a paid refund or an expiry lowers the balance). The credit is a conditional `UPDATE ... WHERE balance_sompi + credit + in-flight <= cap` (and applies the v2.13 expiry policy to `expires_at`); if it matches nothing (the cap moved under a deposit already on chain) nothing is credited or recorded, the settlement goes to `kasgate:deadletter:settlements` as `{prepaidDeposit, reason: "prepaid_cap_exceeded", creditSompi}` and the buyer gets 503 `service_unavailable` ("payment was accepted but could not be credited; contact support"). Debits for that key wait on the row lock while a deposit settles.
- **SSRF (L1).** IPv4-compatible `::/96`, site-local `fec0::/10` and SIIT IPv4-translated `0:0:0:0:ffff:0:0:0/96` (`::ffff:0:a.b.c.d`, RFC 2765) are refused outright by the upstream/webhook resolver guard (`is_forbidden_ip`) and by webhook URL validation (422). Webhook URL validation now uses the same rule as the resolver, so v4-mapped, 6to4, Teredo, NAT64 and SIIT literals of non-public IPv4 are refused at create/update too.
- **Webhook test-fire limits (L2, behaviour change).** `POST /v1/webhooks/{id}/test` is limited per merchant (across all its webhooks) by the Redis fixed-window limiter: setting `rl_webhook_test_per_minute` (default 10) -> 429 `rate_limited` (X402ErrorBody, `Retry-After`); 503 when the limiter is down and `rate_limit_fail_closed` (FastAPI `{detail}` body, same as other /v1/* limiter-down 503s). After each fire only the newest `webhook_test_events_kept` (default 20) finished (`succeeded`/`dead`) `webhook.test` events of that webhook are kept; older ones and their deliveries are deleted. Pending or in-flight test deliveries are never pruned.
- **Limiter 429 body (behaviour change).** Every rate-limit 429, including `/v1/*` (merchant create, auth challenge/verify, unpaid public prepaid/trial reads) and webhook test-fire, uses the same X402ErrorBody as `/p/*` (`error` = `rate_limited`). The earlier "/v1/* keeps FastAPI `{detail}` for 429" rule is withdrawn; 503 from a down limiter on `/v1/*` is still `{detail: "service temporarily unavailable"}`.
- **Secret rotation overlap (L3, behaviour change).** `POST /v1/webhooks/{id}/rotate-secret` keeps the replaced secret signing for `webhook_secret_overlap_seconds` (default 86 400; 0 disables). During the window every delivery's `X-KasGate-Signature` is `t=<unix>,v1=<hex new>,v1=<hex old>` (Stripe-style, current first); afterwards back to one `v1=`. Receivers must accept the delivery when ANY `v1=` verifies (the SDK's `verify_webhook_signature` does). Rotating again inside the window keeps only the secret being rotated out now as the previous one. `WebhookCreated` gains `previous_secret_expires_at` (ISO-8601 UTC, null on create or with a 0 overlap). Storage: the existing Fernet-encrypted `webhooks.secret_encrypted` holds either the bare secret or a strict JSON envelope `{v:1, current, previous, previous_until}`; `secret_prefix` is the new secret's.
- **Signature header parsing (L4).** Verifiers (gateway `verify_signature`, SDK `verify_webhook_signature`) accept `t=` only as 1-12 ASCII digits and `v1=` only as ASCII; anything else (e.g. `t=²`) is simply "not verified", never an exception.
- **Balance privacy (L7, behaviour change).** `GET /v1/prepaid/balance` is public for **`spendable_sompi` and `expires_at` only** (the 402 prepaid offer's `balanceUrl` points here: agents use `spendable_sompi`). `merchant_id`, `payer_address`, `balance_sompi`, `updated_at`, `deposited_sompi`, `debited_sompi`, `refunded_sompi`, `expired_sompi` and `refund_hold_sompi` are **null** unless the request carries both `X-KasGate-Balance-Timestamp: <unix seconds>` and `X-KasGate-Balance-Signature: <128 hex>`, a kaspa `sign_message` (Schnorr) signature by the key behind `payer_address` over
  ```
  KasGate
  Domain: <PUBLIC_BASE_URL netloc, lowercased>
  Purpose: kasgate:v1:prepaid-balance-read
  Address: <payer_address>
  Slug: <slug>
  Timestamp: <unix seconds>
  ```
  with the timestamp within ±300 s. Only one of the headers, a malformed value, a stale timestamp or a signature that does not verify -> **401 `invalid_balance_signature`** (`{error, message}`); no headers -> the public shape. Responses carry `Vary: X-KasGate-Balance-Timestamp, X-KasGate-Balance-Signature` and `Cache-Control: no-store`. The message authorises nothing else (its Purpose differs from every other KasGate text); a replay inside the window only repeats the read.

  **Unsigned `PrepaidBalanceRead` (no signature headers):** every field is present (strict schema); only `spendable_sompi` (string sompi) and `expires_at` (ISO datetime or null) are populated; all of `merchant_id`, `payer_address`, `balance_sompi`, `deposited_sompi`, `debited_sompi`, `updated_at`, `refunded_sompi`, `expired_sompi` and `refund_hold_sompi` are null.

  **Signed `PrepaidBalanceRead` (valid headers) and merchant `GET /v1/prepaid/balances`:** every field is populated: `merchant_id` (uuid), `payer_address`, `balance_sompi`, `deposited_sompi`, `debited_sompi`, `updated_at` (ISO datetime), `refunded_sompi`, `expired_sompi`, `refund_hold_sompi`, `spendable_sompi` (all sompi fields are strings), `expires_at` (ISO datetime or null).

  The buyer SDK signs every `prepaid_balance` read (optional fields still parse an unsigned or older payload) and the MCP `prepaid_balance` tool returns nulls if a gateway omits them. The public `spendable_sompi` plus on-chain deposits can still let an observer estimate leftover credit.

- **Refunds status privacy (behaviour change).** `GET /v1/prepaid/refunds/status` is buyer-signed with the **same headers** as the balance read (`X-KasGate-Balance-Timestamp`, `X-KasGate-Balance-Signature`) over the same message shape with Purpose `kasgate:v1:refunds-status-read` (not the balance Purpose; a signature for one cannot be reused for the other) and the same ±300 s window. Missing, malformed, stale or unverified signatures -> **401 `invalid_balance_signature`** (`{error, message}`). A valid signature returns the existing public `PrepaidRefundRead` list (amounts and statuses visible; `reason`, `last_error` and the claim still withheld). `POST /v1/prepaid/refunds/status` with a signed `status` challenge is unchanged and still returns the full rows. Responses carry `Vary: X-KasGate-Balance-Timestamp, X-KasGate-Balance-Signature` and `Cache-Control: no-store`. The buyer SDK signs every default `prepaid_refunds` GET; `prepaid_refunds(..., signed=True)` still uses the POST challenge. The MCP `prepaid_refunds` tool follows the SDK.
- **By design, not changed.**
  - L5: trial counters are per (endpoint, x-only key) and keys are free, so a key-rotating client can use up an endpoint's `trial_daily_cap` each day. The cap bounds the merchant's cost; the per-IP `rl_trial_calls_per_ip_per_hour` limit is the only Sybil brake.
  - L6: the price in a prepaid debit (or trial) challenge is fixed when it is issued. After a merchant raises a price, challenges minted earlier still debit the old price until they expire (`payment_max_age_seconds`). Merchants who need an instant cut-over should expect up to that window at the old price.
- **New settings:** `rl_webhook_test_per_minute` (10), `webhook_test_events_kept` (20), `webhook_secret_overlap_seconds` (86 400). **New error codes:** `prepaid_cap_exceeded` (422), `invalid_balance_signature` (401). **New headers:** `X-KasGate-Balance-Timestamp`, `X-KasGate-Balance-Signature`.

### v2.12.2 additions (05 privacy residuals, in-flight cap on quotes, orphan sweeper, single-use refunds-status signatures)

- **Unsigned deposit responses carry no balance.** `PrepaidDepositQuote` and `PrepaidDepositReceipt` (including the idempotent 200 replay) no longer have `balance_sompi` or any total that reveals it; the buyer reads it with the signed balance read. Quote: `{slug, merchant_id, payer_address, deposit_sompi, fee_sompi, credit_sompi, required, deposit_url}`. Receipt: `{deposit_id, tx_id, slug, merchant_id, payer_address, deposit_sompi, fee_sompi, credit_sompi, created_at}`. The buyer SDK models keep `balance_sompi` optional so an older gateway still parses.
- **`prepaid_cap_exceeded` is generic.** Quote and deposit alike answer 422 `{error: "prepaid_cap_exceeded", message: "deposit would exceed the prepaid balance cap; use a signed balance read for details"}`: no balance, headroom, credit or cap value (the cap is operator configuration and is not part of the public contract). The quote's cap check now counts in-flight debits like the deposit (one shared rule, `would_exceed_cap`), so a quote's answer matches what the deposit will enforce. The quote error used to be FastAPI's `{detail}`; it is now the standard `{error, message}` shape.
- **Refund challenge.** An omitted `amount_sompi` on a `request` challenge needs the buyer-signed balance-read headers (see Refund challenge in v2.13): omitted and unsigned -> 422 `refund_amount_required` (new code), explicit amounts need no signature. Error texts carry no figures. SDK `prepaid_refund_request(amount=None)` now signs the challenge request; an explicit amount sends no headers.
- **Accepted by design.** `spendable_sompi` is public, and a buyer's on-chain deposits to a merchant are public, so anyone who knows a buyer address can infer (spendable minus the sum of on-chain deposits) the part of the balance that is call-only credit or already spent. Quote and challenge status codes (201 vs 422/409) can also be used to probe headroom or the public spendable total by binary search. Both are accepted: the balance, credit and refundable totals themselves only come from signed reads, and the refundable cap is enforced at the signed refund POST.
- **Orphaned in-flight debits.** A prepaid debit whose upstream call never recorded a status (`status = 'debited'`, `upstream_status_code IS NULL`, e.g. the worker was killed after the debit) holds the buyer's money and, because in-flight debits count against the cap, cap headroom. The debit sweeper (`app/debit_sweeper.py`, started by the app lifespan) refunds each such row older than `PREPAID_DEBIT_ORPHAN_AGE_SECONDS` with the same refund as an upstream 5xx (`refund_prepaid_debit`: row -> `refunded`, amount and its failed-delivery-credit part back on the balance, no clamp). Each refund is ONE conditional `UPDATE ... WHERE status = 'debited' AND upstream_status_code IS NULL AND created_at < now() - age` on the database clock, so it is idempotent, safe on several replicas (a second sweeper matches nothing) and cannot refund a live request that finished or is younger than the age. Settings: `PREPAID_DEBIT_SWEEPER_ENABLED` (true), `PREPAID_DEBIT_SWEEPER_INTERVAL_SECONDS` (60), `PREPAID_DEBIT_ORPHAN_AGE_SECONDS` (900; must be >= 3 x `UPSTREAM_TIMEOUT_SECONDS` + 60, validated at startup), `PREPAID_DEBIT_SWEEPER_BATCH_SIZE` (100). No migration.
- **Refunds-status signatures are single use.** After `GET /v1/prepaid/refunds/status` verifies a signature the gateway does `SET kasgate:sigreplay:refunds-status:{sha256(lower-case signature hex)} NX EX ttl`, `ttl` = the time the signature could still verify (its timestamp + 300 s, at most 601 s). A replay inside that window is **401 `invalid_balance_signature`** (same shape as any bad signature); Redis unavailable -> **503 `service_unavailable`** (fail closed). The message format is unchanged. Clients must sign every call fresh (new timestamp; the SDK never reuses one). An invalid signature stores nothing. The balance-read signature is not single use.

## CONTRACT v2.13 — prepaid refunds and credit expiry (additive; supersedes "there is no withdrawal route" in v2.11)
Buyers can get unused prepaid credit back, and a merchant can make credit expire. KasGate still holds no keys and no coins: the deposit already paid the merchant on-chain, so a refund is an ordinary payment **from the merchant's own wallet to the depositing address**. No platform fee and no treasury output apply to refunds (returned money is never taxed). The on-chain payment rules for calls and deposits are unchanged (output 0 merchant, output 1 treasury, fee max(1.5 %, 0.2 KAS), 0.6 KAS minimum). Webhook `api_version` stays `2.12` (new event types only, same envelope).
- **Balance identity.** `balance = deposited - debited - refunded - expired` (DB CHECK, all totals >= 0). `refund_hold_sompi` is the part of the balance set aside by an open refund request (`0 <= hold <= balance`, DB CHECK). **Spendable** = `balance - hold`, and 0 once `expires_at` has passed. Debit challenges, debits (`/p` with `X-KasGate-Prepaid`) and refund requests use spendable credit only (the conditional debit UPDATE checks both the hold and `expires_at > now()`). `GET /v1/prepaid/balance` and `GET /v1/prepaid/balances` add `refunded_sompi, expired_sompi, refund_hold_sompi, spendable_sompi, expires_at` (unsigned public read: only `spendable_sompi` and `expires_at` are populated, everything else including `balance_sompi` and `updated_at` is null; signed public read and merchant `GET /v1/prepaid/balances` fill every field).
- **Refund challenge.** `POST /v1/prepaid/refunds/challenge` (public, unpaid rate limit; strict body `{slug, payer_address, action: "request"|"cancel"|"status" = "request", amount_sompi?: int, refund_id?: uuid}`). `request`: `amount_sompi` omitted = all *refundable* credit, derived **only for a request that carries the buyer-signed balance-read headers** (`X-KasGate-Balance-Timestamp`, `X-KasGate-Balance-Signature`, Purpose `kasgate:v1:prepaid-balance-read`, see v2.12.1; a bad signature is 401 `invalid_balance_signature`); omitted and unsigned -> 422 `refund_amount_required`; the amount must be >= `MIN_OUTPUT_SOMPI` (0.2 KAS: a smaller payout output is not standard under storage mass) -> else 422 `refund_too_small`; more than the public `spendable_sompi` -> 409 `insufficient_balance`; (the refundable cap itself, which excludes call-only credit, is enforced when the signed request is submitted to `POST /v1/prepaid/refunds`: 409 `insufficient_balance`; the unsigned challenge never reveals or probes it); these error texts are generic and carry no balance, credit or refundable figure; an open refund already exists for this balance -> 409 `refund_already_open`. `cancel`: `refund_id` names this key's open refund (else 404 `refund_not_found`); not cancellable (claimed `paying` and the claim has not lapsed, `payout_submitted`, or any attempted payout still `pending`) -> 409 `refund_not_cancellable` with the reason. `status`: neither field (amount in the text is `0`); 404 when the key has no balance there. -> 201 `{nonce, message, action, slug, merchant_id, payer_address, amount_sompi ("0" for status), refund_id, expires_at}`, stored as `kasgate:prepaid:refund:challenge:{nonce}` EX `payment_max_age_seconds`. Message (sign with kaspa `sign_message`, the depositing P2PK key; its Purpose is unique, so no debit, trial, payer proof or login signature can stand in for it):
  ```
  KasGate
  Domain: {netloc of PUBLIC_BASE_URL}
  Purpose: kasgate:v1:prepaid-refund
  Action: {request|cancel|status}
  Address: {payer_address}
  Merchant: {merchant_id}
  Amount: {amount_sompi, 0 for status}
  Refund: {refund_id or -}
  Nonce: {nonce}
  Expires: {expires_at ISO-8601}
  ```
- **Open / cancel.** `POST /v1/prepaid/refunds` `{nonce, signature}` -> 201 PrepaidRefundRead (status `requested`). `POST /v1/prepaid/refunds/{id}/cancel` `{nonce, signature}` -> 200 (status `cancelled`, hold released). Both are rate limited per client IP (`RL_PREPAID_REFUND_PER_MINUTE`, default 30; 429 `rate_limited`). Order: load challenge (unknown/expired -> 410 `challenge_expired`) -> action matches (else 400) -> for cancel, the challenge's refund matches the path (else 400 `invalid_signature`, **checked before the nonce lock, so it does not burn the challenge**) -> Schnorr signature by the stored key over the rebuilt text (else 400 `invalid_signature`) -> `SET kasgate:prepaid:refund:noncelock:{nonce} NX` (held -> 409 `challenge_replayed`) -> ONE transaction: conditional `UPDATE prepaid_balances SET refund_hold += amount WHERE balance - hold >= amount AND not expired` + insert refund (unique `request_nonce`; partial unique index = one open refund per balance, so racing requests yield one 201 and one 409) + `prepaid.refund.requested` event -> consume the challenge. **Nothing is debited at request time.** The cancel UPDATE is conditional: `status = 'requested'` (or `paying` whose claim lapsed: `claimed_at` older than `PREPAID_REFUND_CLAIM_TTL_SECONDS` or `first_claimed_at` older than `PREPAID_REFUND_CLAIM_MAX_SECONDS`) AND NOT EXISTS a `pending` row in `prepaid_refund_payouts`.
  - **Cancel of a refund the merchant ever claimed** (`first_claimed_at` set; it is never cleared). After the signature check and BEFORE the nonce lock, the gateway asks the node (`engine.find_refund_payouts(payout_address, amount_sompi, refund_id, min_daa_score=first_claimed_daa_score)`): mempool entries received by the payout address that carry this refund's payload (any amount; `payload_seen`), and accepted UTXOs to it of exactly `amount_sompi` (not coinbase; payload not readable there) whose `blockDaaScore` is greater than the virtual DAA stored at the first claim (`first_claimed_daa_score`; outputs already accepted then are ignored; if the node could not be asked at claim time the score is null and this filter is skipped). Transactions it already knows (any attempt, any KasGate settlement or deposit) are skipped. Anything new is recorded as a payout attempt with method `scan` (refund -> `payout_submitted`, re-checked by the worker like any attempt; at most `PREPAID_PAYOUT_MAX_PENDING_ATTEMPTS` new `scan` attempts are recorded per cancel, and they do not count toward the merchant's tx_id cap) and the cancel is refused with 409 `refund_not_cancellable` naming the tx ids. If the node cannot be asked -> 503 `service_unavailable`. Neither burns the challenge. A UTXO of exactly the amount accepted after the claim that is not this payout (rare) blocks the cancel until that attempt is confirmed invalid, proven by the merchant, or abandoned after `PREPAID_PAYOUT_ATTEMPT_MAX_SECONDS`.
  - **Cooldown hold.** Such a cancel (ever claimed) does NOT release the hold: the refund is `cancelled` with `hold_until = now + PREPAID_REFUND_CANCEL_COOLDOWN_SECONDS` (1800; 0 = release at once) and the amount stays in `refund_hold_sompi` (not spendable, not expirable) until the ledger worker releases it after `hold_until` **and no attempt for this refund is still pending**. A payout posted inside the cooldown keeps the hold until that attempt is confirmed (debited in full from the hold, `late_paid_from = cancelled`, `shortfall_sompi = 0`) or resolved invalid/abandoned. A cancel of a never-claimed refund releases the hold at once (`hold_until` null): there is no scan and no cooldown.
- **Status.** `GET /v1/prepaid/refunds/status?slug=&payer_address=&limit<=50` -> this key's refunds at that merchant, newest first, **buyer-signed** with `X-KasGate-Balance-Timestamp` + `X-KasGate-Balance-Signature` over Purpose `kasgate:v1:refunds-status-read` (same scheme and ±300 s window as the balance read; unsigned or invalid -> **401 `invalid_balance_signature`**; each signature is single use, see v2.12.2; rate limited). The list still has `reason` and `last_error` **withheld (null)** and **the claim hidden**: `paying` reads as `requested` and `claimed_at`, `first_claimed_at`, `claim_expires_at` are null, so nobody can time a cancel to the moment a claim lapses. `POST /v1/prepaid/refunds/status` `{nonce, signature}` of a `status` challenge (single use, `RL_PREPAID_REFUND_PER_MINUTE`) -> the same rows (up to 50) WITH the merchant's reasons, payout errors and the claim details.
- **PrepaidRefundRead** `{id, merchant_id, payer_address, amount_sompi, status, tx_id, reason, last_error, created_at, updated_at, claimed_at, first_claimed_at, hold_until, claim_expires_at, payout_submitted_at, paid_at, resolved_at, late_paid_from, shortfall_sompi, payout_address, payout_payload_hex, payout_payload}`. States:
  - `requested` -> `paying` (merchant claim) -> `payout_submitted` (attempt recorded) -> `paid`;
  - `requested | paying` -> `rejected` (merchant) or `cancelled` (buyer, see above);
  - `payout_submitted` -> `requested` (**reverted**: every attempt proven invalid, an attempt abandoned, or no attempt confirmed within `PREPAID_PAYOUT_PENDING_MAX_SECONDS`), with `prepaid.refund.payout_reverted`;
  - `cancelled | rejected` -> `paid` with `late_paid_from` set (**late payout backstop**, below).
  `tx_id` is the latest attempt while `payout_submitted` and the confirmed payout once `paid`. `claim_expires_at` (computed, only while `paying`) = min(`claimed_at` + `PREPAID_REFUND_CLAIM_TTL_SECONDS`, `first_claimed_at` + `PREPAID_REFUND_CLAIM_MAX_SECONDS`). `hold_until`: see cooldown hold. `payout_address` = the depositing address; `payout_payload` = `kasgate:v1:refund:<refund id hex>` (text), `payout_payload_hex` = its hex.
- **Merchant [Bearer].**
  - `GET /v1/prepaid/refunds?status=&limit<=200&offset` (newest first; unknown status -> 422 `invalid_status`).
  - `POST /v1/prepaid/refunds/{id}/claim` -> 200 `paying` (`claimed_at` = now, `first_claimed_at` and `first_claimed_daa_score` set only on the first claim — a null score from a node outage stays null forever, `claim_expires_at` returned) from `requested` or `paying` (renews the claim); else 409 `refund_not_claimable`. **Call it before broadcasting** (e.g. right before KasWare `sendKaspa`) and broadcast only well before `claim_expires_at`; renew first if needed. From then on the buyer cannot cancel. A claim lapses after `PREPAID_REFUND_CLAIM_TTL_SECONDS` (900) without a payout, and renewals are refused (409 `refund_not_claimable`, "claim window used up") once `first_claimed_at` is older than `PREPAID_REFUND_CLAIM_MAX_SECONDS` (3600); the merchant can still pay and post the payout, or reject. `first_claimed_at` (and the DAA) survive a payout revert, so after the window a reverted refund cannot be claimed again (pay unclaimed, or reject); the scan and cooldown still apply. A lapsed claim is not a free cancel: see "Cancel of a refund the merchant ever claimed". The gateway-broadcast `{transaction}` mode is the safest flow (recorded before broadcast, no claim needed).
  - `POST /v1/prepaid/refunds/{id}/reject` `{reason: 1..300 chars}` -> 200 `rejected`, hold released, only from `requested`/`paying` with no pending attempt (else 409 `refund_not_rejectable`).
  - `GET /v1/prepaid/refunds/{id}/payouts` -> PrepaidRefundPayoutRead[] oldest first `{id, refund_id, tx_id, method: tx_id|transaction|scan, status: pending|confirmed|invalid|duplicate|abandoned, payload_verified, check_count, last_error, next_check_at, confirmed_at, resolved_at, created_at}`.
  - `GET /v1/prepaid/ledger?limit&offset` -> PrepaidLedgerEntryRead `{id, payer_address, kind: refund|expiry, direction, amount_sompi, balance_after_sompi, tx_id, refund_id, note, created_at}`.
  Another merchant's refund is 404.
- **Payout.** `POST /v1/prepaid/refunds/{id}/payout` with EXACTLY one of `{tx_id}` or `{transaction}`. **Both must carry the payload `kasgate:v1:refund:<refund id hex>`** and an output paying the buyer address **exactly** `amount_sompi` (any position; change back to the merchant is fine). The payload is what binds a transaction to one refund: a buyer's own self-transfer or another merchant's payout of the same amount to the same buyer cannot be claimed.
  - **Recorded first.** The attempt is stored in `prepaid_refund_payouts` (unique `tx_id`) and an open refund is moved to `payout_submitted` (tx_id = this attempt) in ONE transaction **before** the node is asked (tx_id mode) or the transaction is broadcast (transaction mode). A tx_id already attempted for another refund -> 409 `payout_replayed`. Re-posting one of this refund's tx_ids reuses its attempt; a **corrected tx_id is a new attempt and both stay on record and are re-checked**. At most `PREPAID_PAYOUT_MAX_PENDING_ATTEMPTS` (3) pending `{tx_id}` attempts of one refund; a new bare tx_id beyond that -> 409 `too_many_attempts`. A signed `{transaction}` (checked locally) and a `scan` attempt do not count toward this cap and are never refused by it. An `abandoned` attempt is **never revived by `{tx_id}`** (409 `payout_abandoned`); only a `{transaction}` proof may revive an abandoned or invalid attempt, and it keeps its original `created_at` (the abandonment clock never restarts). `POST /payout` is rate limited **per merchant** (`RL_REFUND_PAYOUT_PER_MERCHANT_PER_MINUTE`, 20; 429 `rate_limited`).
  - `{tx_id}`: a payment the merchant broadcast. KasWare: `kasware.sendKaspa(payout_address, amount_sompi, {payload: payout_payload})` (KasWare hex-encodes the UTF-8 string, which gives exactly these payload bytes; it resolves to the signed transaction JSON, whose `id` is the tx_id). A KasGate settlement or prepaid deposit txId -> 422 `invalid_payout`. `engine.verify_payout(tx_id, payout_address, amount_sompi, refund_id, payload_checked=)` reads the sink hash, then the mempool entries received by the buyer address (whole transaction: outputs AND payload), then polls the virtual chain until accepted (UTXO index once as fallback). A transaction seen only in the UTXO index (accepted and out of the mempool) counts only if its payload was seen earlier (`payload_verified`); otherwise it stays pending with `payload_unverified` and the merchant should post the signed transaction JSON as `{transaction}` (KasWare's `sendKaspa` return value), which proves the payload locally. Allowed in tx_id mode for a `cancelled`/`rejected` refund too (late payout, below). Same tx_id on a `paid` refund -> 200 (idempotent); another tx_id -> 409 `refund_closed`.
  - `{transaction}`: a merchant-signed kaspa Transaction JSON (<= MAX_RAW_TX_CHARS) that the gateway broadcasts; only for open refunds (else 409 `refund_closed`). `engine.payout_tx_id(...)` checks payload and outputs locally and computes the id, the attempt is recorded, then `engine.submit_payout(...)` broadcasts. Local check failure -> 422 `invalid_payout`; node refusal -> 422 `tx_rejected` (attempt `invalid`, refund back to `requested` unless another attempt is pending; re-posting the same transaction retries it); node unreachable -> **202** (the broadcast may have happened: kept `pending` and re-checked).
  - **Acceptance in every mode.** A payout is marked paid only once the virtual chain accepts it, also under `settlement_mode=mempool` (a mempool sighting with the right payload is recorded as `payload_verified` and confirmed later).
  - Accepted -> **200 `paid`**: in ONE transaction the attempt becomes `confirmed`, the refund `paid`, `balance` and `refund_hold` drop by the amount, `refunded_sompi` grows, a `prepaid_ledger_entries` row (kind `refund`, the payout `tx_id`, unique `refund_id`) is written and `prepaid.refund.paid` is queued. Not confirmed yet -> **202 `payout_submitted`** (`last_error` says why). Definite wrong payout (wrong amount/address/payload, `wrong_network`) -> 422 `invalid_payout`; the attempt is `invalid` and the refund goes back to `requested` only if no other attempt is pending.
  - **Ledger worker** (`LEDGER_POLL_INTERVAL_SECONDS`, 30): re-checks every `pending` attempt that is due (`next_check_at`), **including attempts of refunds that were reverted, cancelled or rejected meanwhile**. Only `invalid_payout`/`wrong_network` resolves an attempt as `invalid`. Not visible / not accepted / payload not proven: re-checked after an **age-based backoff** = attempt age x `PREPAID_PAYOUT_UNSEEN_BACKOFF_FRACTION` (0.1), capped at `PREPAID_PAYOUT_BACKOFF_MAX_SECONDS` (a fresh attempt at once, a 1 h old one after 6 min, a day-old one every 30 min); when the refund has been `payout_submitted` longer than `PREPAID_PAYOUT_PENDING_MAX_SECONDS` (86400) it reverts to `requested` (hold kept, merchant may pay again) but its attempts stay pending; an attempt older than `PREPAID_PAYOUT_ATTEMPT_MAX_SECONDS` (604800) is `abandoned`. Any other error (node outage, malformed node reply) never reverts: the attempt is retried with backoff `PREPAID_PAYOUT_BACKOFF_BASE_SECONDS * 2^n` capped at `PREPAID_PAYOUT_BACKOFF_MAX_SECONDS` (30 s .. 1800 s). An attempt that confirms after another one already paid the refund is `duplicate` (the merchant paid twice; the ledger moves once).
  - **Late payout backstop.** If an attempt confirms for a refund that is already `cancelled` or `rejected`, the coins reached the buyer anyway: the refund becomes `paid` with `late_paid_from`, the balance is re-debited by up to the amount (a refund still in its cooldown hold is debited in full from that hold; otherwise a newer open refund of the same balance that is **not being paid** is closed as `rejected` with a reason so its hold can be taken; a newer refund that is `payout_submitted`, has any pending attempt, or is `paying` with a claim that has not lapsed is **never** closed: the difference is recorded as shortfall instead and the merchant decides), `shortfall_sompi` records what could not be debited, a ledger row (amount may be 0) and `prepaid.refund.paid` (with `late_paid_from`, `shortfall_sompi`) are written. The credit never stays spendable or refundable twice.
- **Credit expiry.** `PATCH /v1/merchants/me` `{display_name?, prepaid_expiry_days?: 1..3650 | null}` sets the merchant default (null = never; MerchantRead gains `prepaid_expiry_days`). Endpoints gain `prepaid_expiry_days` (create/update/read; null = use the merchant default). The policy is applied **at deposit time** through the endpoint used: `expires_at = max(existing, now + days)` (each deposit extends). Never retroactive: credit deposited while the policy was "never" (`expires_at IS NULL` with spendable credit) stays non-expiring when a later deposit lands under a policy; a "never" policy deposit clears the expiry. Before a deposit is credited, overdue credit on that balance is expired in the same transaction. The ledger worker sweeps due balances (`FOR UPDATE SKIP LOCKED`, `LEDGER_BATCH_SIZE`): the spendable part (balance minus any open refund hold, which stays payable) moves to `expired_sompi`, with a ledger row (kind `expiry`) and `prepaid.credit.expired`. Expired credit stops paying calls immediately, even before the sweep.
- **Webhook events** (data fields): `prepaid.refund.requested|paid|rejected|cancelled` `{refund_id, payer_address, amount_sompi, status, tx_id, reason, late_paid_from, shortfall_sompi, hold_until, balance_sompi}` (+ `endpoint_slug` on requested; `hold_until` set on a cancel with a cooldown hold); `prepaid.refund.payout_reverted` `{refund_id, payer_address, amount_sompi, status: "requested", tx_id: null, reason, late_paid_from, shortfall_sompi, hold_until, pending_tx_ids: comma-separated attempts still re-checked | null, error}` (one event per revert); `prepaid.credit.expired` `{ledger_entry_id, payer_address, expired_sompi, balance_sompi, refund_hold_sompi, expired_at}`. Other event ids are `event_id_for(type, refund id | ledger entry id)`, so each fires once.
- **Error codes** (all in the `X402ErrorBody.error` vocabulary): `invalid_payer`, `invalid_signature`, `invalid_cursor`, `invalid_status`, `challenge_expired`, `challenge_replayed`, `refund_too_small`, `refund_amount_required`, `refund_already_open`, `refund_not_found`, `refund_not_cancellable`, `refund_not_claimable`, `refund_not_rejectable`, `refund_closed`, `invalid_payout`, `payout_replayed`, `payout_abandoned`, `too_many_attempts`, plus the shared `insufficient_balance`, `endpoint_not_found`, `wrong_network`, `tx_rejected`, `rate_limited`, `service_unavailable`.
- **Client IP behind a proxy.** Every per-IP rate limit (auth challenge/verify, merchant create, unpaid `/p`, trial calls, prepaid/refund challenge, status and balance reads, refund writes) uses `client_ip` as follows. The **web app** (server-side calls to the gateway) forwards at most one client IP in `X-Forwarded-For`: the `TRUSTED_PROXY_HOPS`-th entry from the right of the incoming `X-Forwarded-For` chain (`TRUSTED_PROXY_HOPS` is a web-app setting, default `0` = do not forward; entries further left were supplied by the client and are ignored). The **gateway** honours `X-Forwarded-For` only when the TCP peer is in `TRUSTED_PROXY_IPS` (JSON list of IPs/CIDRs, default `[]` = off). When the peer is trusted, it walks the header from the right and skips hops that are themselves in `TRUSTED_PROXY_IPS`, so the client is the right-most hop that is not a trusted proxy (or the left-most hop if every hop is trusted). `X-Forwarded-For` from any other peer is ignored, so a buyer cannot pick their own rate-limit bucket. **List only the fixed IP of your own reverse proxy or of the web app** (e.g. that container's static address); never a whole Docker bridge or host network range: every client whose connection arrives from such a range (with Docker port publishing, often all host traffic) could then choose its own rate-limit bucket. Listing the Next.js server takes effect only when the web app actually forwards an IP (`TRUSTED_PROXY_HOPS` > 0 and a usable hop); with the default `0` the gateway sees the web app's own address.

- **Limits.** A payout whose payload was never seen by the gateway (it left the mempool before the merchant posted its tx_id) cannot be confirmed by `tx_id` alone: post the signed transaction JSON as `{transaction}` (kaspa SDK `Transaction.to_dict()` form; KasWare's `sendKaspa` return value works only where it parses as that form, which this branch has not verified against a live wallet; if it does not, the gateway answers 422 `invalid_payout` and the refund stays pending until `PREPAID_PAYOUT_ATTEMPT_MAX_SECONDS`). Re-posting an already-broadcast transaction is safe (the node treats it as a duplicate). A wallet that cannot set a payload cannot pay by `tx_id`; build and sign the transaction with the payload (kaspa SDK) and post it as `{transaction}`. A refund amount below 0.2 KAS cannot be requested (spend it on calls instead). Expiry is per balance, not per deposit bucket. The remaining shortfall risk is a `tx_id` payout the gateway never saw in time to keep the credit held:
  - the merchant **never claimed** (API users who post a tx_id directly get no pre-cancel scan and no cooldown, so a cancel between broadcast and post releases the credit at once); or
  - they claimed, then broadcast **after** both the claim window and the cooldown had ended, and the payout was not visible to the node when the buyer cancelled; or
  - the payout was **accepted at or before `first_claimed_daa_score`** (broadcast before or at the first claim): the pre-cancel UTXO scan ignores it, so after a cancel and the cooldown the credit can be released. If the node could not be asked at the first claim, `first_claimed_daa_score` is null and stays null (a renewal never backfills it), and this UTXO filter is skipped.
  Such a payout is still recorded late with a shortfall, which is between the merchant and the buyer. **Claim before broadcasting** (the dashboard UI flow already does this: claim, then KasWare `sendKaspa`), broadcast well before `claim_expires_at`, or use `{transaction}` mode (recorded before broadcast, no claim needed). A payout posted inside the cooldown no longer has this risk: the hold stays until the attempt is resolved.

## CONTRACT v2.14 — failed-delivery auto-credit (additive, after v2.13)
Depends on CONTRACT v2.13 (PR #1, Alembic `0008_prepaid_refunds`) and must be read with it; this branch merges #1 and must be merged after it. Migration `0009_failed_delivery_credits` follows 0008 and cannot be applied first. The on-chain payment rules are unchanged (output 0 merchant, output 1 treasury, fee max(1.5 %, 0.2 KAS), 0.6 KAS minimum). Webhook `api_version` stays `2.12` (new event types only, same envelope).

When a settled payment's last upstream delivery **failed** in a creditable way and redelivery is closed, the gateway credits the merchant share (`merchant_amount_sompi`, output 0) to the payer key's prepaid balance with that merchant (`kasgate-prepaid-v1`), clamped to `PREPAID_MAX_BALANCE_SOMPI`. This happens at most once per `tx_id`. The on-chain payment and the platform fee (output 1) are not reversed. Failed-delivery credit is **call-only and non-refundable**. k402 `kaspa-utxo` payments, non-P2PK payers and prepaid deposits are never credited. A credited settlement is no longer redeliverable (409 `payment_replayed`).
- **Delivery outcome (explicit, per settlement).** `settlements.delivery_outcome` is written `pending` in the same transaction as the settlement (and again when a redelivery is claimed), before the upstream call, then set to `delivered` (any upstream status below 500) or `failed` with `delivery_failure` = `upstream_5xx` | `connect_error` | `timeout` | `oversized`; `credited` once credited. Only `failed` is ever credited; NULL (settled before 0009) or `pending` (the outcome write was lost, or the process died mid-call) is **never** a credit. A failed outcome write is logged at ERROR and its JSON pushed to the Redis list `kasgate:deadletter:delivery-outcomes` (alert on it like `kasgate:deadletter:settlements`); the buyer still gets the upstream's answer. If a settlement is still `pending` after `REDELIVERY_WINDOW_SECONDS + ceil(UPSTREAM_TIMEOUT_SECONDS) + FAILED_DELIVERY_CREDIT_GRACE_SECONDS` (same horizon as the credit sweep, compared on the database clock, inside the lookback), the ledger worker logs ERROR once (`delivery outcome still pending after the redelivery window`) and stamps `pending_alerted_at`. That is the alert; the row is not credited. Operators reconcile `delivery_outcome` by hand.
- **What is creditable.** `upstream_5xx` and `connect_error` always (while the policy is on); `timeout` unless the merchant excludes timeouts (`credit_timeouts=false`). Never `oversized` (the upstream answered; the gateway refused to relay it, 502 `upstream_response_too_large`) and never any known status below 500.
- **Policy stamped at settle time.** The merchant policy in force when the call settles is stamped on the settlement (`failed_delivery_credit_policy` = `errors` | `errors_and_timeouts`, NULL = opted out). A later toggle never adds or drops credit for calls already paid.
- **When.** `attempts_exhausted`: `delivery_attempts >= REDELIVERY_MAX_ATTEMPTS`, or `REDELIVERY_WINDOW_SECONDS=0`. Credited inline; the failing response (the relayed 5xx, or 502 `upstream_error`) carries `X-KasGate-Credit: Base64(JSON{creditId, kind, txId, merchantId, creditSompi, balanceSompi, reason, shortfallSompi?})` when `creditSompi > 0`. `creditId` is the `prepaid_ledger_entries.id`, the same value as `credit_id` on each item of signed `POST /v1/prepaid/credits/status`. The header is in `PAYMENT_HEADERS` (stripped both ways, so an upstream cannot forge it) and exposed via CORS. `window_expired`: `settled_at + REDELIVERY_WINDOW_SECONDS + ceil(UPSTREAM_TIMEOUT_SECONDS) + FAILED_DELIVERY_CREDIT_GRACE_SECONDS <= now()` (grace default 30 s; the wait is derived from the configured upstream timeout, so one in-flight attempt always finishes first). Credited by the ledger worker's sweep (`FAILED_DELIVERY_CREDIT_LOOKBACK_SECONDS`, default 7 days, batch `LEDGER_BATCH_SIZE`). The sweep and the redelivery claim both compare against the **database clock** (`now()`).
- **Balance identity** (supersedes v2.13): `balance = deposited + credited - debited - refunded - expired` (DB CHECK; `credited_sompi >= 0`). `credit_balance_sompi` is the unspent call-only credit: `0 <= credit_balance_sompi <= LEAST(credited_sompi, balance - refund_hold)` (DB CHECK).
- **Call-only, non-refundable.** Prepaid debits spend `credit_balance_sompi` **first**, then deposited sompi (`prepaid_debits.credit_sompi` records the split; a restored debit gives the credit part back to `credit_balance_sompi`). `refundable = max(0, balance - refund_hold - credit_balance)` = deposited and unspent only (`refund_hold` includes both an open refund and a v2.13 cancel cooldown until the ledger worker releases it). The result is never negative. A refund request (v2.13) may take at most `refundable` (default amount = `refundable`; above it 409 `insufficient_balance`, below the minimum output 422 `refund_too_small`), so the refund hold never covers credit and credit still pays calls while a refund is open. A late payout of a cancelled/rejected refund (v2.13) re-debits deposited sompi first and only then credit (the coins already reached the buyer). Expiry drops the unspent credit with the rest of the spendable balance. `GET /v1/prepaid/balance(s)` add `credited_sompi`, `credit_balance_sompi` and `refundable_sompi`. The unsigned `POST /v1/prepaid/refunds/challenge` does not: `spendable_sompi` and `refundable_sompi` are omitted so unspent call-only credit cannot be derived from the unauthenticated response (`amount_sompi` is still the amount to sign, defaulting to refundable).
- **Cap.** A credit never lifts the balance above `PREPAID_MAX_BALANCE_SOMPI`, counting in-flight prepaid debits (`status = 'debited' AND upstream_status_code IS NULL`) exactly as a deposit does: `credit = min(share, max(0, cap - balance - in_flight))`, `shortfall = share - credit`. The ledger row keeps `shortfall_sompi` (a fully clamped credit is a row with `amount_sompi = 0`, `shortfall_sompi > 0`, and still closes the settlement as `credited`). Each shortfall fires a signed `prepaid.credit.failed_delivery_shortfall` webhook.
- **Expiry.** A credit extends the balance expiry like a deposit, using the v2.13 policy **in force at credit time**, never retroactively: `expires_at = max(current expires_at, now + policy days)`; a later existing expiry is never shortened; credit promised "never" stays non-expiring; a "never" policy credit clears the expiry. Overdue credit on that balance is expired first, in the same transaction.
- **Merchant policy (opt-out, merchant-level only).** Default on, timeouts included. `GET /v1/prepaid/failed-delivery-policy` [Bearer] -> `{enabled, credit_timeouts, enabled_at, disabled_at}`. `PUT` with `{enabled?, credit_timeouts?}` (at least one) changes it for calls settled from then on. No per-endpoint override (out of scope).
- **Merchant list.** `GET /v1/prepaid/credits?slug=&payer_address=&tx_id=&limit<=200&offset` [Bearer] -> list[PrepaidCreditRead] `{id, kind, tx_id, settlement_id, endpoint_id, slug, payer_address, payment_scheme, amount_sompi, fee_sompi, credit_sompi, shortfall_sompi, balance_after_sompi, reason, delivery_failure, upstream_status_code (>= 500 or null), delivery_attempts, settled_at, created_at}`, newest first. `GET /v1/prepaid/ledger` lists these rows too (with `settlement_id`, `slug`, `credit_reason`, `shortfall_sompi`).
- **Buyer view.** `POST /v1/prepaid/credits/challenge` (public, unpaid rate limit; strict body `{slug, payer_address}`) -> 201 `{nonce, message, action: "credits", slug, merchant_id, payer_address, amount_sompi: "0", refund_id: null, expires_at}`. The challenge is stored in the same Redis key as a refund challenge (`kasgate:prepaid:refund:challenge:{nonce}`, EX `payment_max_age_seconds`) and uses the same message layout and Purpose (`kasgate:v1:prepaid-refund`); `Action: credits`, `Amount: 0`, `Refund: -`. The unsigned challenge does not include `spendable_sompi` or `refundable_sompi`; the signed status body is the only source for those values. A missing balance is still a valid challenge (the status reply is zeros and an empty list). `POST /v1/prepaid/credits/status` `{nonce, signature, before?, limit?}` (single use — **each page needs a fresh challenge**, `RL_PREPAID_REFUND_PER_MINUTE`, same claim/consume path, key binding and action check as refunds/status). `limit` defaults to 10, max 100 (else 422). `before` is the opaque `next_cursor` from a previous page (keyset over `(created_at, id)` newest first, bound to this merchant and depositing key). The cursor is unsigned base64url of `v1|{created_at}|{credit_id}|{merchant_id}|{public_key}`: it is tamper-evident by that binding (a forged cursor only moves the window over this signer's own rows, or is 400 `invalid_cursor`), not a secret — do not treat it as one in logs. `created_at` on each credit row is the database clock (`now()`), not the app clock. -> 200 `BuyerCreditStatus` `{merchant_id, credited_sompi, credit_balance_sompi, refundable_sompi, credit_count, credits: [{credit_id, tx_id, slug, credit_sompi, shortfall_sompi, reason, created_at}], next_cursor}`. `credit_id` is the ledger entry UUID (the same value as `creditId` on `X-KasGate-Credit`). `credit_count` is the total, not the page size. `next_cursor` is a string, or null when there are no more pages. A malformed `before`, or one issued for another buyer or merchant, including a timestamp that overflows UTC conversion, is 400 `invalid_cursor` (the nonce is not burned; the body does not include credits). A `status` challenge cannot be used here, and a `credits` challenge cannot be used on refunds/status (400 `invalid_signature`; the nonce is not burned). Errors: 400 `invalid_payer` / `invalid_signature` / `invalid_cursor`, 404 `endpoint_not_found`, 409 `challenge_replayed`, 410 `challenge_expired`, 422 validation, 503 `service_unavailable`. The v2.13 `GET` and signed `POST /v1/prepaid/refunds/status` replies stay bare JSON arrays of refunds and carry no credit header. No other public credit lookup (out of scope). SDK/MCP parsing of `X-KasGate-Credit` and of this endpoint is a follow-up.
- **Webhooks.** `prepaid.credit.failed_delivery` (when `credit_sompi > 0`) `{ledger_entry_id, kind, settlement_id, tx_id, payment_scheme, endpoint_id, endpoint_slug, payer_address, amount_sompi, fee_sompi, credit_sompi, shortfall_sompi, balance_sompi, reason, delivery_failure, upstream_status_code, delivery_attempts, settled_at}`; `prepaid.credit.failed_delivery_shortfall` (when `shortfall_sompi > 0`) carries the same fields plus `merchant_share_sompi` and `max_balance_sompi`. ## Notes from the funded testnet-10 run
- Node RPC UTXO entries return scriptPublicKey as a hex string "<u16 BE version><script>" (e.g. "0000"+"20<xonly>ac"), not only the dict form; parsers MUST accept both.
- A paid call whose upstream fails (5xx/connection error) is NOT refunded on-chain; buyers retry with the same PAYMENT-SIGNATURE within redelivery_window_seconds (max redelivery_max_attempts).
- Test/dev hosts with synthetic DNS (every name -> 198.18.0.1) are correctly blocked by the SSRF guard; use an IP-literal public upstream such as https://1.1.1.1/cdn-cgi/trace for funded tests.
